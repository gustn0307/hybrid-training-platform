# 오늘 학습한 내용

## Spring Security와 JWT의 역할

Spring Security는 요청의 인증 상태를 확인하고 접근 권한을 적용하는 프레임워크다. JWT는 사용자 식별 정보와 클레임을 담을 수 있는 토큰 형식이다.

JWT를 사용한다고 인증·인가가 자동으로 완성되는 것은 아니다. Spring Security가 토큰 검증 결과를 인증 정보로 연결하고 보호 기능의 접근 여부를 판단하도록 구성해야 한다. 이 프로젝트에서 사용자 인증 책임은 Spring Boot에 있으며 FastAPI는 사용자 토큰을 관리하지 않는다.

## Access Token과 Refresh Token

Access Token은 보호된 API에 접근할 때 사용하는 인증 정보다. Refresh Token은 Access Token을 다시 발급받는 데 사용하는 별도의 자격 정보이며 일반 API 접근용 토큰과 역할이 다르다.

Refresh Token 도입은 필수로 가정하지 않는다. 토큰의 유효기간과 저장·전달·갱신·폐기 방식은 정책 검토와 승인이 필요한 사항이다. 이번에는 Access Token 30분, Refresh Token 미사용으로 확정하고 React 메모리에만 토큰을 보관하도록 구현했다.

## JWT 로그아웃과 서버 측 무효화

서명과 만료만 검사하는 JWT 인증에서는 클라이언트가 토큰을 삭제해도 이미 발급된 토큰을 서버에서 계속 유효하다고 판단할 수 있다.

FR-AUTH-004는 로그아웃으로 종료한 인증 정보로 보호 기능에 접근할 수 없어야 한다고 정의한다. 따라서 화면의 토큰 삭제와 서버의 기존 인증 정보 사용 차단을 구분해야 한다. 이번에는 JWT마다 jti를 발급하고 로그아웃한 jti를 PostgreSQL에 만료 시점까지 보관하도록 구현했다. 서버 재시작 후에도 무효화 상태가 유지되는지 검증했다.

## DTO 입력 검증과 비즈니스 규칙 검증

DTO 입력 검증은 요청에 필요한 값이 있는지, 형식과 허용 범위가 맞는지 확인한다. 비즈니스 규칙 검증은 저장된 데이터와 현재 상태까지 고려하여 요청을 처리할 수 있는지 판단한다.

예를 들어 이메일 형식 검사는 입력 검증이고, 이미 사용 중인 이메일인지 확인하는 것은 데이터 조회가 필요한 규칙 검증이다. 운동 프로필도 최초 설정과 기존 정보의 부분 수정을 구분해야 한다. 이번에는 승인된 입력 허용값을 백엔드에 정의하고 React가 그 목록을 사용하도록 연결했다.

## 인증과 인가

인증(Authentication)은 요청한 사용자가 누구인지 확인하는 과정이고, 인가(Authorization)는 그 사용자가 특정 기능이나 데이터에 접근할 수 있는지 판단하는 과정이다.

로그인이나 토큰 검증에 성공해도 다른 사용자의 운동 프로필에 접근할 수 있어서는 안 된다. 본인 데이터만 조회·수정할 수 있다는 조건은 인증 성공과 별도로 검증해야 한다.

## 회원 정보와 운동 프로필 분리

회원 정보는 이메일, 보호된 비밀번호와 닉네임 등 계정 식별·인증을 위한 정보다. 운동 프로필은 운동 목표, 경험 수준, 주요 운동 유형과 사용 가능한 장비 등 운동 계획의 입력 정보다.

두 정보는 책임과 변경 시점이 다르다. 회원가입 직후 운동 프로필이 미설정인 상태를 표현하고, 운동 정보 수정이 인증 정보 변경으로 이어지지 않도록 구분한다. 이번 1차 범위에서 운동 프로필 수정과 유예된 닉네임 수정도 구별해야 한다.

# AI Love Workout에 적용한 내용

작업 시작 시점에는 10월 28일에 구축·검증한 실행 골격이 있었다. 이후 승인 정책을 문서에 먼저 반영하고 Spring Boot·PostgreSQL·React의 AUTH + USER Vertical Slice를 구현했다.

* FR-AUTH-001~004: 회원가입·로그인·로그아웃을 구현했다. 가입 후 별도 로그인하며 Access Token은 30분, Refresh Token은 사용하지 않는다. 토큰은 React 메모리에만 보관하고 새로고침 시 재로그인한다.
* 로그아웃한 JWT의 jti를 PostgreSQL에 저장하고 보호 요청마다 무효화 여부를 확인한다. 기존 토큰 재사용 차단과 서버 재시작 후 무효화 유지, DB 장애 중 로그아웃 실패 처리를 검증했다.
* FR-USER-001, FR-USER-003~004: 계정 조회와 운동 프로필 최초 설정·조회·부분 수정을 구현했다. Spring Security의 인증 주체로 본인만 접근하게 하고 수정 요청에서 누락한 항목은 유지한다. FR-USER-002 닉네임 수정의 유예는 유지한다.
* 비밀번호는 8~72자·추가 조합 제한 없음·BCrypt 저장 정책을 적용했다. SHA-384 → Base64 → BCrypt 형식은 유지하면서 잘못된 UTF-16 surrogate를 가입·로그인에서 400으로 거부하고 해싱 단계의 손실성 인코딩도 차단했다. 정상 한글·이모지와 기존 해시의 호환성을 검증했다.
* 이메일은 백엔드의 형식 검증·소문자 정규화·254자 제한을 기준으로 유지했다. React 입력을 text + inputMode=email로 바꿔 Unicode 이메일 제출 차단을 없애고, 빈 입력·길이 검사와 서버 오류 안내를 확인했다.
* 초기 구현에서 자동 테스트 47개가 통과했다. 필수 결함 수정과 회귀 테스트 추가 후 최종 82개가 통과했으며 PostgreSQL 통합 38개, 단위·MVC 44개이고 실패·오류·건너뜀은 0이다. React 타입 검사·빌드와 수정한 서비스의 Docker 빌드도 성공했다.
* 보안 수정 후 첫 전체 회귀 실행에서는 기존 프로필 테스트 16개가 사전 회원가입 단계의 DB 503으로 실패했다. 환경 연결 상태 확인 후 추가 코드 변경 없이 같은 코드로 재실행해 82개가 모두 통과했다. 최초 실패 원인은 확정하지 않았다.
* 사용자가 Chrome에서 가입 후 로그인 화면 전환, 로그인, 운동 프로필 최초 설정·저장·조회, 수정 화면 진입, 변경 없이 저장 시 안내, 로그아웃과 로그인 화면 표시를 직접 확인했다. 로그아웃 이전 JWT 재사용 시 401과 새로고침 후 재로그인도 확인했다.
* 실제 프로필 값 변경 후 재조회하는 Chrome 수동 검증 여부는 미확인이다. 해당 동작은 PostgreSQL 통합 테스트와 Edge headless 검증으로 확인했다. Edge에서는 ASCII·Unicode 이메일의 실제 폼 제출과 전체 사용자 흐름도 각각 통과했다.

근거는 [FR](../requirements/functional-requirements.md), [API 계약](../architecture/portfolio-mvp-api.md), [초기 구현·검증 기록](../development.md), 현재 코드와 최종 JUnit 보고서다. HTTPS 배포와 SESSION / RECORD / PLAN / NLP 구현은 남아 있다.

# Codex 리뷰에서 배운 점

* UTF-16 surrogate는 반드시 올바른 쌍인지 확인해야 한다. 문자 수만 검사하면 잘못된 입력이 UTF-8 변환 중 다른 문자로 치환되어 서로 다른 비밀번호가 같은 해시에 일치할 수 있다. DTO 검증과 엄격한 인코딩을 함께 적용해야 한다.
* 브라우저의 type=email과 백엔드 Bean Validation은 허용 범위가 같지 않다. 백엔드가 허용한 Unicode 이메일을 UI가 막지 않도록 검증 기준을 맞추고 서버를 최종 기준으로 유지해야 한다.
* 자동 테스트는 규칙·저장·예외 처리를 확인하고 브라우저 테스트는 폼 제출과 실제 화면 흐름을 확인한다. 기존 47개 통과만으로 경계 입력까지 보장할 수 없었으며, 수동 Chrome 검증과 자동 headless 검증의 범위도 구분해야 한다.
* DB 연결 실패는 비즈니스 로직 실패와 분리해 조사해야 한다. 503을 성공으로 바꾸거나 검증을 약화하지 않고 환경을 확인한 뒤 같은 코드로 재실행했다. 재실행 통과만으로 최초 실패의 원인을 단정할 수는 없다.
