# 오늘 학습한 내용

## SDD에서 명세와 구현의 추적성

SDD는 명세를 기준으로 설계하고 구현하는 개발 방식이다. 사용자 스토리, FR, API, 데이터 모델과 테스트가 연결되어야 기능이 왜 필요한지와 무엇을 검증해야 하는지 설명할 수 있다.

일정이 짧아져도 이 연결을 없애지 않는다. 이번에 구현할 사용자 흐름에 필요한 명세와 미결정 사항부터 검토하고 작은 단위로 설계·구현·검증을 이어 간다.

## MVP Scope와 단기 구현 범위

MVP Scope는 제품 가설을 검증하기 위해 승인한 전체 범위이고, 단기 구현 범위는 특정 기한까지 먼저 완성할 대상을 정한 것이다.

두 범위를 구분하면 일부 기능을 먼저 시연하더라도 원래 MVP 전체가 완료된 것처럼 설명하지 않을 수 있다.

## 범위 축소와 요구사항 삭제

웨이트나 닉네임 수정을 이번 구현에서 유예해도 기존 Must 요구사항 자체가 사라지는 것은 아니다. 요구사항과 ID를 보존하고 이번 구현에 포함하지 않는 부분을 별도 문서에 남겨야 후속 작업과 테스트를 추적할 수 있다.

## Vertical Slice로 사용자 흐름 연결하기

Vertical Slice는 하나의 사용자 행동이 화면, API, 비즈니스 규칙, 저장과 조회까지 이어지도록 작은 흐름 단위로 개발하는 방식이다.

예를 들어 일반 입력으로 운동 기록을 저장하고 다시 조회하는 흐름을 먼저 연결한 뒤 자연어 구조화와 계획 반영을 추가할 수 있다. 매 단계에서 실제 사용자 흐름을 검증하여 통합 문제를 일찍 발견하는 데 도움이 된다.

## Human-in-the-loop와 규칙 기반 추천의 책임

AI는 자연어 운동 결과를 구조화하지만 사용자 확인 없이 최종 기록으로 저장하지 않는다. 사용자는 결과를 확인하고 수정한 뒤 저장을 확정한다.

운동 계획의 핵심 내용은 규칙이 결정하고 AI는 해석과 설명을 돕는다. 계획 후보의 수정·확정·거절과 운동 세션 시작도 분리하여 사용자의 최종 결정권을 유지한다.

## 프로세스 Health Check와 Dependency Health Check

프로세스 Health Check는 서비스가 요청에 응답하는지 확인하고, Dependency Health Check는 서비스가 사용하는 DB와 내부 서비스의 연결까지 확인한다.

Spring Boot의 /api/v1/health와 /api/v1/health/dependencies를 분리했다. AI 서비스가 중지되었을 때 의존성 점검은 503을 반환했으며, 프로세스 응답 성공을 전체 시스템 준비 완료로 해석하면 안 된다는 점을 확인했다.

## Mock 테스트와 실제 통합 검증

Mock 기반 테스트는 DB나 외부 응답을 제어하여 처리 조건과 HTTP 계약을 확인하지만 실제 연결 성공을 증명하지는 않는다.

Docker Compose에서 네 서비스를 실행한 뒤 PostgreSQL 쿼리와 헬스 API, Vite 프록시 경유 통신을 별도로 검증했다. React 빌드·HTTP 응답 확인도 브라우저의 시각·상호작용 검증과 구분해야 한다.

## JDK 실행 버전과 Java 컴파일 대상

설치된 JDK 21로 빌드·실행하면서 Gradle의 --release 17로 언어·바이트코드·표준 API 사용 범위를 Java 17에 맞췄다. javap으로 major version 61을 확인했지만, 이것이 실제 JDK 17에서 실행을 검증했다는 의미는 아니다.

## React → Spring Boot → FastAPI 통신 구조

개발 환경에서 React의 /api 요청은 Vite 프록시를 거쳐 Spring Boot로 전달되고, Spring Boot가 내부 FastAPI를 호출한다. 프록시 경유 HTTP 검증으로 이 경로와 DB 연결을 확인했다. FastAPI가 사용자 인증을 담당하거나 React가 FastAPI를 직접 호출하도록 구성하지 않았다.

## 코드 주석의 목적

주석은 자명한 동작을 반복하기보다 설계 의도, 비즈니스 규칙과 중요한 제약을 설명해야 한다. AGENTS.md에 규칙을 추가하고 접근 제어, 외부 호출 타임아웃, 예외 상세 정보 보호, 비동기 요청 취소 등의 이유를 기존 코드에 보완했다. 비즈니스 로직과 API 계약은 변경하지 않았다.

# AI Love Workout에 적용한 내용

* 러닝과 맨몸운동을 1차 구현 대상으로 정하고 웨이트 및 일부 기능은 후속 구현으로 유예한다.
* 기존 APPROVED 요구사항은 보존하고 portfolio-mvp-scope-2026-11-01.md에 포함·유예 대상과 완료 기준을 기록했다.
* 자연어 운동 기록 → 사용자 확인·수정 → 저장 → 다음 운동 계획 반영이라는 핵심 가치를 유지한다.
* 일반 입력 기록 저장·조회 흐름부터 연결하고 계획과 AI 기능을 통합하는 작업 순서를 따른다.
* 기록 저장에는 진행 중인 세션이 필요하며 빈 세션 종료 확인과 미완료 입력 보호 정책을 유지한다.
* 명세·설계·테스트 추적성과 리뷰 원칙을 유지한다. 최소 설계와 로컬 환경 구축은 완료했고, 누락 FR 상세화와 비즈니스 기능 구현은 후속 작업으로 남겼다.
* 인증 토큰, 운동 규칙, 기록 단위와 초안 보존 등 미결정 정책은 임의로 확정하지 않는다.
* 최소 Domain Model, ERD, API 설계 문서 세 개를 작성하고 현재 구현과 후속 구현 대상을 구분했다. 도메인 엔티티·테이블을 구현한 것은 아니다.
* React / Spring Boot / FastAPI / PostgreSQL 실행 골격과 Docker Compose 통합 환경을 구축했다.
* 네 서비스의 연결, PostgreSQL 실제 쿼리, Spring Boot·FastAPI Health와 Dependencies Health를 검증했다. AI 장애 시 503 응답과 재시작 후 정상 복구도 확인했다.
* Spring Boot 자동 테스트 8개, FastAPI 자동 테스트 3개가 통과했고 React TypeScript 타입 검사와 빌드가 성공했다. 결과는 docs/development.md의 실행 검증 기록을 근거로 한다.
* AGENTS.md에 향후 작성·수정 코드에 적용할 주석 작성 규칙 16개를 추가하고 기존 코드의 필요한 주석을 보완했다.

# Codex 리뷰에서 배운 점

* 최소 설계 문서 작성, 실행 골격 구축, 비즈니스 기능 완료는 서로 다른 결과이므로 분리해서 기록해야 한다.
* 프로세스 응답, Mock 테스트, 실제 서비스 연결 검증은 각각 확인하는 범위가 다르다. 헬스 응답만으로 운동 기록이나 AI 구조화 기능까지 완료했다고 설명할 수 없다.
* 코드 주석도 설계 의도를 전달하는 문서다. 주석 보완 시 실행 코드·설정·API 계약이 바뀌지 않았는지 확인해야 한다.
* 시작 계획을 남기는 것에 더해 종료 시점의 검증 결과와 미완료 항목까지 기록해야 다음 작업을 정확히 이어갈 수 있다.
