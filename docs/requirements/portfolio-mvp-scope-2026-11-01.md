# AI Love Workout 포트폴리오 MVP 1차 구현 범위

## 문서 정보

* 프로젝트: AI Love Workout
* 결정일: 2026-10-28
* 목표 완료일: 2026-11-01
* 상태: APPROVED
* 성격: 기존 MVP 범위의 변경이 아닌 1차 구현 범위 제한

---

## 1. 문서 목적

2026-11-01까지 취업 포트폴리오로 시연할 AI Love Workout의 1차 구현 범위와 완료 기준을 정의한다.

약 3개월 만에 작업을 재개한 시점에 실행 가능한 서비스 코드가 없는 상태를 고려하여, 핵심 사용자 흐름을 연결하는 구현에 집중한다. 이 문서의 APPROVED는 구현 범위에 대한 승인이며 구현, 테스트 또는 배포 완료를 의미하지 않는다.

## 2. 기존 MVP와의 관계

* 기존 전체 MVP의 기준은 [mvp-scope.md](mvp-scope.md)이며 APPROVED 상태와 내용을 유지한다.
* 기존 승인 요구사항을 삭제하거나 우선순위를 변경하지 않는다. 이번 결정은 1차 구현 대상과 후속 구현 대상을 구분하는 것이다.
* 기존 Must인 웨이트 지원과 닉네임 수정은 이번 1차 구현에서 명시적으로 유예한다. 기존 MVP에서 제외하거나 완료한 것으로 취급하지 않는다.
* 웨이트를 포함하는 기본 운동 정보, 계획 후보 및 자연어 구조화 요구사항은 러닝·맨몸운동 부분만 우선 구현한다. 해당 FR 전체를 구현 완료로 표시하지 않는다.
* 1차 구현 범위의 완료는 원래 MVP 전체 완료와 구분한다. 기존 MVP 전체 완료 여부는 기존 범위와 인수 조건을 기준으로 별도 판단한다.
* SDD(Specification-Driven Development, 명세 기반 개발)와 Project Rules를 유지한다. 사용자 스토리 → FR → 설계·API·데이터 모델 → 테스트의 추적성을 보존한다.
* SESSION, RECORD, NLP, HISTORY의 상세 FR은 아직 작성되지 않았다. 관련 사용자 스토리를 근거로 1차 구현에 필요한 상세 명세와 미결정 정책을 먼저 검토하고, 설계와 구현으로 연결한다.
* 이번 작업에서는 본 문서와 당일 Study·Meeting·Journal만 생성하며 기존 요구사항과 ADR은 수정하지 않는다.

## 3. 1차 구현 목표

> 사용자가 러닝과 맨몸운동 결과를 자연어로 입력하고, AI 구조화 결과를 확인·수정한 뒤 진행 중인 운동 세션에 저장하면, 저장된 최근 기록이 다음 규칙 기반 운동 계획 후보에 반영되는 흐름을 시연한다.

일반 입력에 의한 기록 저장 경로를 먼저 연결하고 계획 및 AI 기능을 단계적으로 통합한다. 각 기능은 화면만 완성하는 것이 아니라 요청, 비즈니스 규칙, 저장과 조회를 연결하는 Vertical Slice 단위로 구현한다.

러닝 기록은 거리, 운동 시간, 평균 페이스와 운동 일시를 포함하며 평균 페이스는 거리와 운동 시간으로 계산한다. 맨몸운동 기록은 운동 종목, 반복 횟수 또는 수행 시간, 세트 수와 운동 일시를 포함한다. 입력의 허용 범위와 세부 검증 기준은 미결정 정책 검토 후 명세화한다.

운동 프로필 수정은 기본 운동 정보 수정이며, 이번에 유예하는 계정 닉네임 수정과 구분한다.

## 6. 유지해야 할 비즈니스 규칙

### 6.1 인증 및 사용자 정보

* 인증된 사용자는 자신의 프로필, 운동 세션, 기록과 계획 후보에만 접근할 수 있어야 한다.
* 로그아웃으로 종료된 인증 정보로 보호 기능에 접근할 수 없어야 한다. 구체적인 무효화 방식은 인증 설계에서 결정한다.
* 기본 운동 정보 미설정 상태는 정상 조회 결과로 제공하고 임의의 저장값을 만들어 제공하지 않는다.
* 최초 운동 프로필 설정에는 필요한 전체 정보가 있어야 하며 기존 정보 수정 시 미입력 항목은 유지한다.
* 기본 운동 정보 변경이 이미 생성된 후보나 확정 운동 계획을 자동으로 변경하지 않는다.

### 6.2 운동 계획 후보

* 운동 계획의 핵심 조건과 수행 내용은 운동 규칙으로 결정한다. AI가 임의로 전체 운동 계획을 결정하지 않는다.
* AI는 자연어 해석, 후보 설명과 추천 이유의 자연어 표현을 돕는다. 최종 선택과 확정은 사용자가 수행한다.
* 후보 생성 요청 한 건에 후보 한 개를 제공한다. 최근 기록이 없는 신규 사용자는 기본 운동 정보를 운동 규칙에 적용한다.
* 사용자가 선택한 러닝·맨몸운동 유형을 모두 포함하고 선택하지 않은 유형이나 사용할 수 없는 장비가 필요한 종목을 임의로 포함하지 않는다.
* 운동 유형별 배정 시간, 전환 시간과 휴식 시간의 합은 가용 시간을 초과하지 않는다. 모두 구성할 수 없으면 후보를 생성하지 않고 이유와 변경 가능한 조건을 안내한다.
* 추천 이유는 최소 한 개 이상 제공하고 실제 후보 생성에 반영한 정보에 근거한다.
* 현재 후보만 수정·확정·거절할 수 있다. 후보 수정은 FR-PLAN-006의 해당 운동 유형에 적용되는 허용 항목과 원자적 처리 정책을 따른다.
* 수정 결과는 가용 시간과 장비 조건을 만족해야 한다. 종목 삭제로 생긴 잔여 시간을 자동 배분하거나 시간 초과를 맞추기 위해 사용자 입력값을 임의로 줄이지 않는다.
* 오늘 운동 가능한 시간과 선택 유형 변경은 후보 수정이나 재생성이 아닌 FR-PLAN-001의 신규 생성 흐름으로 구분한다. 장비는 기본 운동 정보에서 수정하고 휴식 시간은 후보 편집 대상으로 추가하지 않는다.
* 후보 수정 후 최초 추천 이유는 최초 생성 당시의 설명으로 유지하며 수정된 현재 후보 전체에 대한 새 설명으로 취급하지 않는다.
* 후보 수정·확정·거절은 운동 세션을 자동으로 시작하지 않는다. 동일 후보의 반복 확정은 실패 처리하고 기존 확정 계획을 변경하지 않는다.
* 거절한 후보는 삭제하거나 기존 내용을 변경하지 않으며 더 이상 수정·확정·재거절할 수 없다. 사용자는 별도 동작으로 계획 없는 세션을 시작하거나 흐름을 종료할 수 있다.

### 6.3 세션, 기록 및 미완료 입력

* 모든 최종 운동 기록은 진행 중인 운동 세션에 포함하여 저장한다. 계획 후보나 확정 계획 자체를 실제 수행 기록으로 취급하지 않는다.
* 한 사용자에게 진행 중인 세션이 있으면 새 세션을 바로 생성하지 않고 기존 세션의 계속 진행 또는 종료를 안내한다.
* 세션 시작·종료 시각과 총 세션 시간을 관리하며 하나의 세션은 기록을 포함하지 않거나 하나 이상 포함할 수 있다.
* 기록 없는 세션 종료 전 사용자 확인을 받고, 해당 세션은 통계와 후보 생성용 최근 기록에서 제외한다.
* AI 구조화 결과는 사용자가 확인·수정하여 저장을 확정하기 전까지 최종 운동 기록으로 저장하지 않는다.
* 저장되지 않은 자연어 입력이나 구조화 결과가 있으면 종료 요청 시 안내하고 계속 작성, 입력 폐기 또는 종료 요청 취소를 제공한다.
* 종료 요청 취소는 세션을 CANCELLED로 변경하는 의미가 아니다. 진행 중인 세션을 유지한다.
* 구조화가 실패해도 일반 입력으로 기록을 저장할 수 있어야 한다. 원문·초안의 보존 위치와 기간, 누락값 처리의 세부 정책은 별도 결정한다.
* 통증·질환 정보는 일회성 입력을 포함해 수집하거나 계획 생성에 활용하지 않는다.

## 7. 기술 스택과 아키텍처

* 프론트엔드: React, TypeScript, Vite 방향을 유지한다.
* 공개 API 및 인증: Java 17, Spring Boot, Spring Security와 Gradle 방향을 유지한다.
* AI 서비스: Python과 FastAPI를 사용하고 기존 OpenAI API 활용 방향을 유지한다. 구체적인 모델과 버전은 이 문서에서 확정하지 않는다.
* 데이터 저장: PostgreSQL 구조를 유지한다. Redis 기반 최적화는 1차 구현에서 유예한다.
* 프론트엔드는 Spring Boot와 통신하고 Spring Boot가 내부 인터페이스로 FastAPI를 호출한다.
* 사용자 인증·인가와 토큰 관리는 Spring Security가 담당하며 FastAPI는 사용자 인증 토큰을 발급하거나 관리하지 않는다.
* 서버 타임스탬프는 UTC로 저장하고 사용자 시간대는 별도로 관리한다.
* 외부 설정은 환경 변수로 관리하고 비밀값 및 민감한 건강·인증 데이터를 문서, 저장소 또는 애플리케이션 로그에 노출하지 않는다.
* 외부 연동은 제공자별 어댑터로 격리한다. 향후 외부 데이터를 가져올 때 원본 payload와 사용자 수정 데이터를 분리하는 기존 원칙을 유지한다.
* 개발 도구 버전·구동 구성과 실제 배포 대상은 아직 미확정이다. 기존 Docker·AWS 등의 방향을 구체적인 배포 완료 상태로 해석하지 않는다.

## 8. 완료 기준

아래는 향후 검증할 기준이며 현재 완료 결과가 아니다.

* 가입·로그인 후 본인 프로필 조회 및 운동 프로필 최초 설정·수정을 수행할 수 있다.
* 일반 입력으로 러닝·맨몸운동 기록을 진행 중인 세션에 저장하고 조회·수정·삭제할 수 있다.
* 자연어 운동 기록 → AI 구조화 → 사용자 확인·수정 → 저장 → 날짜별 조회 → 다음 후보에 최근 기록 반영 흐름이 HTTPS 환경에서 연결된다.
* 러닝의 거리와 운동 시간으로 평균 페이스를 계산하고, 입력에 필수값이 없는 경우 보완 흐름을 확인한다. 예를 들어 “15분 뛰고 푸시업 10회 3세트”에는 러닝 거리가 없으므로 사용자 보완 없이 저장 완료 시나리오로 취급하지 않는다.
* 후보의 시간 배분·수행 내용·추천 이유를 확인하고 수정·확정·거절할 수 있다. 후보 확정과 세션 시작이 분리된다.
* 후보 거절 후 계획 없는 세션 시작, 중복 진행 세션 방지, 빈 세션 종료 확인 및 미완료 입력 보호 흐름을 검증한다.
* AI 구조화 실패 후에도 일반 입력으로 기록 저장을 완료할 수 있다.
* 인증·소유권, 세션 전이, 기록 검증·페이스 계산, 계획의 시간·장비 조건, 후보 수정 원자성·반복 확정 차단 등 주요 비즈니스 로직의 백엔드 자동화 테스트가 존재하고 통과한다.
* 테스트에서 관련 사용자 스토리와 FR을 추적할 수 있고 실제 실행 결과와 미검증 항목을 구분한다.
* README와 시연 자료에서 실행 방법, 1차 지원 범위, 유예 기능과 원래 MVP 전체 완료 여부를 구분한다.
* 기존 FR의 상태는 이번 범위 문서 작성만으로 변경하지 않는다. 기능 완료 판단은 실제 구현·검증 결과를 근거로 별도 수행한다.

## 9. 위험 요소 및 대응

| 위험 요소 | 대응 및 남은 확인 |
| --- | --- |
| 실행 코드가 없는 상태에서 5일 내 구현·검증·배포 필요 | 필수 사용자 흐름을 우선 연결하고 Should/Could 및 유예 기능을 추가하지 않는다. 완료 목표는 검증 결과와 구분한다. |
| SESSION·RECORD·NLP·HISTORY 상세 FR 부재 | 사용자 스토리를 근거로 필수 FR과 최소 도메인·API·데이터 관계를 먼저 검토한다. 이 문서로 상세 FR을 대체하지 않는다. |
| 인증 토큰 및 입력 검증 정책 미결정 | 토큰 종류·수명·갱신·보관·무효화와 이메일·비밀번호·닉네임 검증 정책을 별도 확정한다. 임의의 세부값을 넣지 않는다. |
| 운동 종목·계획 산정 규칙 미결정 | 지원 종목, 프로필 허용값, 가용 시간 범위, 최근 기록 기간, 수행값·배정 시간·휴식 산정 규칙을 구현 전에 검토한다. |
| 기록 단위·미완료 초안 처리 방식 미결정 | 여러 입력의 병합, 원문·초안 보존, 인증 만료 시 입력 보호, 기록 삭제와 빈 세션 조회 정책을 검토한다. |
| AI 실패 또는 필수값 누락 | 사용자 확인·수정과 일반 입력 대체를 유지하고 누락값 보완 동작을 명세화한다. |
| 기존 ADR과 최신 요구사항의 표현 차이 | 규칙 기반 계획 책임, 후보 역할·생명주기, 초안과 최종 저장의 구분을 대조하고 ADR 최신화 범위를 결정한다. 이번 단계에서는 ADR을 수정하지 않는다. |
| 환경·배포 대상 미확정 | 개발 환경과 HTTPS 배포 경로를 초기에 확인한다. 실제 배포 대상·계정·설정과 데이터 영속성은 별도 검토한다. |
